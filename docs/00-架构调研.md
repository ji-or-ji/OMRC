# LAN 远程桌面：架构调研与选型

> 目标：局域网内，安卓控 Win / Win 控 Win。
> 功能：文件传输、远程操控（虚拟显示器 + 屏幕尺寸自适应 + 指定显示器采集）、终端、扩展屏、虚拟设备（触摸/鼠标/键盘/数位板）。

---

## 一、先把需求拆开：这不是一个项目，是五个

| # | 子系统 | 难度 | 对体验的决定性 | 备注 |
|---|---|---|---|---|
| 1 | 视频链路（采集→编码→传输→解码→显示） | ★★★★★ | 90% | 全项目的命脉，也是唯一可能让你放弃的部分 |
| 2 | 输入注入（含虚拟触控/笔/键盘） | ★★★☆ | 高 | 坑不在代码，在游戏/UIPI/权限 |
| 3 | 虚拟显示器（IddCx 驱动） | ★★★ | 中高 | 卡点在驱动签名，不是技术 |
| 4 | 多路复用（文件/终端/剪贴板/音频） | ★★★ | 中 | 协议活，可复用现成做法 |
| 5 | UI 与动画 | ★★ | 低 | 最想做，但最不重要 |

**排序的含义**：第 1 项做不通，后面四项全是空中楼阁。所以第一周就要去撞第 1 项，而不是先搭 UI。

## 二、结论先行

### 2.1 关于 Godot：不建议作为主框架

四个理由，按致命程度排：

**① 没有实时视频解码通路（致命）**

Godot 核心至今没有硬件解码。2017 年就有 proposal（godotengine/godot#12362），十年了还开着。

2026 年 11 月刚上架的 `Native Video`（claytercek）确实做到了零拷贝硬件解码，但它解的是 **MP4/MOV 文件容器**（走 Media Foundation 的 `IMFSourceReader`），不是"从网络收 H.264 NAL 单元持续喂进去"。远程桌面要的是后者。

现有能用的替代只有 `godot-videodecoder` 这类 GDExtension，全是 FFmpeg **软件**解码。1080p60 H.264 软解在手机上要吃掉 30~50% CPU，跑一小时手机烫得握不住。远程桌面是要挂着跑几小时的应用。

**要自己做，就是自己写 GDExtension**：Windows 要 Media Foundation MFT + D3D12 共享纹理导入 Godot 的 RenderingDevice，Android 要 MediaCodec + SurfaceTexture + OES 纹理 + RenderingDevice 外部纹理导入。**这等于把全项目最难的部分，乘以平台数，再乘一遍**。

**② 渲染模型错配**

Godot 是持续渲染的游戏循环，默认 60fps 常驻重绘。远程桌面 80% 时间是静态画面，理想状态是**零 GPU 占用**。开启 `low_processor_mode` 能让它闲下来，但动画一闲就卡；不开启则笔记本风扇一直转、手机一直耗电。

你要的其实是"事件驱动的 UI + 一条独立的高帧率视频层"，Godot 天生是反过来的。

**③ 应用层基础设施全靠插件补**

远程桌面恰恰是"输入法、剪贴板、多窗口、权限"密度最高的应用类型：

- 安卓中文输入法：Godot 的 IME 一直是弱项
- 系统文件选择器、SAF
- 剪贴板图片/文件列表
- 前台服务保活（安卓会杀后台）
- 多窗口、通知、无障碍

这些在原生里一行调用的事，在 Godot 里要写平台插件。

**④ 唯一成立的形态，工程量反而更大**

Godot 只做 UI 图层，视频用原生 `SurfaceView`/`SurfaceTexture` 沉在底下，Godot 层半透明叠控件。技术上可行（Godot Android 的 Activity 可以加 View）。但你要维护两套坐标系、两套输入分发、两套生命周期，比直接用原生 UI 更累。

> **如果动画冲动很强烈**：用 `Flutter + Rive/Lottie` 或 `Compose Multiplatform + Rive`。Rive 的矢量动画能力足够撑"复杂动画"，同时生态是完整的。RustDesk 就是 Flutter 做的 Android + Windows 双端远程桌面，这是最硬的经验证据。

### 2.2 "多端统一"的正确解法，不是统一 UI 框架

这是整个调研里最反直觉的一点。

任何 UI 框架，最终都会在这四件事上被逼回原生：视频表面、输入法、文件选择器、生命周期与权限。所以 UI 框架实际只负责**外壳**，而外壳恰恰是这个应用最不值钱的部分。

正确拆法是：

```
统一核心（Rust）：协议 / 采集抽象 / 编解码抽象 / 输入抽象 / 传输
        ↓  FFI / JNI
各端原生壳：Android = Kotlin+Compose+SurfaceView
            Windows = WinUI3/WPF/Avalonia+D3D11 SwapChain
```

核心统一，壳各写各的。壳的代码量占比不到 20%，而且平台差异本来就该在壳里。

**不要为了省 20% 的壳，去牺牲 80% 的核心**。这是选 Godot / 选单一 UI 引擎最常见的账算错的地方。

## 三、三条可选路线

### 路线 A：站在巨人肩上（最快见到画面）

- **Host**：Sunshine（LizardByte，C++，GPLv3）。已经做完了 DXGI 抓屏、NVENC/AMF/QSV/x264、HDR、输入注入、VDD 集成（需外挂 Virtual Display Driver）。
- **Client**：Moonlight Android（GPLv3），已有硬解码。
- **自己加**：文件传输、终端、虚拟数位板（Sunshine 未必覆盖）。

优点：一周内看到画面。缺点：
- GPLv3 传染，你自己也得开源（如果你只自用，其实无所谓）
- 为**游戏串流**设计：固定帧率、单显示器、专用全屏。办公场景要的高分辨率文字清晰度、多显示器、动态分辨率，要改不少
- C++ 代码库，改起来难受

**适合**：目标只是"我要一个能用的东西"，且接受 GPL。

### 路线 B：自研核心（推荐，如果你想真正做出来）

- Rust 核心 + 各端原生壳，或 Rust 核心 + Flutter。
- 学习曲线陡，但每一层你都懂，出问题能修，能按"办公远程桌面"而不是"游戏串流"来优化。

**适合**：你想享受造的过程，也想做出一个真能长期用的东西。

### 路线 C：fork RustDesk（最快得到全功能）

RustDesk：Rust + Flutter，Windows host、Android client、文件传输、终端、虚拟显示器（自带 VDD）、LAN 直连、自建服务端。你列的需求它覆盖了 80%。

- 优点：起点极高，改得动（Rust 代码质量不错）
- 缺点：AGPL-3.0 强传染；代码库庞大且有历史包袱；性能定位是"办公级"不是"游戏级"；UI 深度定制成本高

**适合**：你的真实诉求是"受够了付费软件，我要一个自己能改的"，而不是"我要从零造"。

## 四、核心技术选型

### 4.1 Windows 采集

| API | 能力 | 坑 |
|---|---|---|
| **DXGI Desktop Duplication**<br>(`IDXGIOutputDuplication`) | GPU 侧、零拷贝、按显示器、光标可分离 | 全屏独占的 DX 游戏会返回 `DXGI_ERROR_ACCESS_LOST`；DRM 内容黑屏；模式切换要重建 |
| **Windows.Graphics.Capture**<br>(Win10 1903+) | 支持**窗口级**捕获，Win11 无黄色边框 | WinRT，与 C++/Rust 绑定繁琐；Win10 有黄框 |
| PrintWindow / BitBlt | 兼容性最好 | 慢，1~2 帧/秒级别，仅兜底 |

**建议**：DXGI 主路，WGC 兜底（全屏游戏、单窗口分享）。两者输出统一成一张 D3D11 纹理。

**光标必须单独处理**：Desktop Duplication 的 `GetFramePointerShape` 给你光标位图 + 热点坐标。把光标作为独立小消息以 60Hz+ 发过去，客户端本地绘制。这一条能让"100ms 视频延迟"的主观感受降到"30ms"。GFN、Parsec 全靠这个。

### 4.2 编码

| 路径 | 优点 | 缺点 |
|---|---|---|
| **Media Foundation 硬件 MFT** | **一条代码通吃 NVIDIA/AMD/Intel** | 延迟略高于原生，参数控制弱 |
| NVENC 原生 (`nvEncodeAPI`) | 最低延迟，参数最全 | 只 N 卡，需 CUDA/D3D11 互操作 |
| AMF 原生 | A 卡最优 | 只 A 卡 |
| oneVPL / QSV | I 卡最优 | 只 Intel |
| x264 / SVT-AV1 软编 | 到处能跑 | 吃 CPU，1080p60 要 2~3 核 |

**建议**：MVP 用 Media Foundation 硬件 MFT（一条路先通），优化期再做 NVENC/AMF 原生后端。

**参数底线**（低延迟三件套）：
- 无 B 帧（`frameIntervalP = 0`）
- 无 lookahead / 无前向参考
- CBR，无限 GOP，按需强制 IDR
- `CODECAPI_AVLowLatencyMode = TRUE`
- 桌面内容建议 `profile = High`，不做 deblocking 之外的锐化

**码率参考**（1080p，H.264）：
| 场景 | 码率 |
|---|---|
| 纯文字/办公 | 8~15 Mbps（文字要糊主要怪码率太低） |
| 混合 | 15~25 Mbps |
| 视频/游戏 | 25~50 Mbps |

H.265 省 30~50%。安卓 8.0+ 全系硬解；Win10 需装 HEVC 扩展，Win11 自带。**MVP 先用 H.264 保兼容**。

**进阶（不急）**：混合编码。静态区域走 dirty-rect + LZ4/Zstd 无损，视频区域走硬编。RDP 和 Parsec 都是这个思路，文字清晰度提升巨大，但复杂度翻倍。

### 4.3 传输与协议

局域网场景有个重要前提：**丢包率接近零，RTT < 1ms**。

这意味着 WebRTC 那套抗弱网机制（拥塞控制、抖动缓冲、FEC）在这里几乎没有收益，反而增加延迟。这是可以大幅简化的地方。

| 方案 | 判断 |
|---|---|
| libwebrtc | 功能最全，编译最痛，包体巨大。LAN 场景杀鸡用牛刀 |
| Pion (Go) / webrtc-rs (Rust) | 值得考虑，但要自己接硬编硬解 |
| libdatachannel | 轻量，但只有 DataChannel + SRTP，视频层要自己搭 RTP |
| QUIC (quinn / msquic) | 流 + 多路复用 + 加密都在，Datagram 扩展可发视频。视频层仍需自己补 |
| **自定义 UDP + 简单 NACK** | **LAN 最优解**：延迟最低、代码最少、完全可控 |

**推荐**：

- **视频通道**：UDP。自定义包头 `{seq, frame_id, slice_id, ts, flags}`，MTU 1200 分片。接收端按 frame 重组，缺片发 NACK，等不到就请求 IDR。不做拥塞控制，只做"发太满时降码率"的简易反馈。
- **控制通道**：TCP 或 QUIC，可靠有序。输入事件、文件传输、终端、剪贴板全走这里。
- **一次握手，两条通道**。

留好抽象层：将来要跨网（公网/VPN），把 UDP 视频层换成 WebRTC 的传输即可，上层不用动。

### 4.4 安卓解码与渲染

```
Socket → 环形缓冲 → MediaCodec(async) → SurfaceView
```

关键点：
- **`SurfaceView` 而不是 `TextureView`**。SurfaceView 有独立图层，合成器直接上屏，少一次 GPU 拷贝，延迟低一档。
- `SurfaceHolder.setFixedSize(w, h)` 固定缓冲尺寸，避免每次缩放。
- `MediaFormat.KEY_LOW_LATENCY`（API 30+）、`KEY_PRIORITY`、`KEY_OPERATING_RATE`。
- `configure(format, surface, null, 0)`，`releaseOutputBuffer(index, true)` 立即上屏。
- 异步模式（`setCallback`）比同步 `dequeue` 稳。

**vsync 是隐藏的 16ms**：不要在 `onDraw` 里等 vsync，按帧的 PTS 直接提交，容忍撕裂换取低延迟。

### 4.5 输入注入

这是最容易被低估、坑最多的一块。

| 设备 | API | 说明 |
|---|---|---|
| 鼠标（绝对） | `SendInput` + `MOUSEEVENTF_ABSOLUTE` | 归一化 0~65535 |
| 鼠标（相对/高精度） | `SendInput` 相对位移 | 会被系统加速度影响，要 `SPI_SETMOUSE` 关掉 |
| 触控 | `InitializeTouchInjection` + `InjectTouchInput` | **用户态，无需驱动**，支持多指与压力 |
| **笔/数位板** | **`InjectSyntheticPointerInput`**（Win10 1809+） | `POINTER_INPUT_TYPE_PEN`，可带 pressure / tiltX / tiltY / rotation / barrel / eraser。**这就是虚拟数位板的正解，且用户态即可** |
| 键盘 | `SendInput` + scancode | 中文输入走 `KEYEVENTF_UNICODE`，别发按键序列 |
| 游戏手柄 | ViGEmBus 驱动 | 虚拟 Xbox 手柄 |
| 游戏内的鼠标/键盘 | Interception 驱动 | 内核级 HID 注入，反作弊会检测 |

**注意**：以上用户态注入对普通应用完全够用，但**部分游戏和反作弊会忽略**。如果"远程打游戏"是硬需求，需要上 Interception。纯远程办公不需要。

### 4.6 虚拟显示器

Windows 没有"创建虚拟显示器"的公开 API，唯一正路是 **IddCx（Indirect Display Driver）**，即写一个用户态显示驱动。

**不要自己写驱动**。直接集成现成的开源实现：

- `VirtualDrivers/Virtual-Display-Driver`（活跃维护，支持 4K/8K、自定义分辨率与刷新率、HDR，被 Sunshine 社区广泛使用）
- 备选：Parsec VDD（许可不明，谨慎）、usbmmidd_v2（老旧）

自研的话，卡点不是代码而是**签名**：自签名要用户开测试模式并关驱动签名强制（体验极差），买 EV 证书走 attestation 签名约 $200~400/年。

**屏幕尺寸自适应的完整流程**：

```
客户端连上 → 上报 {宽, 高, DPI, 刷新率}
  → 调用 VDD 控制接口增/改一个虚拟显示器到该模式
  → SetDisplayConfig（CCD API）把它摆到虚拟桌面正确位置
  → 若为"扩展屏模式"，设为主显示器或指定位置
  → 把该 output 设为采集目标
断开 → 删除虚拟显示器，恢复原布局
```

配套 API：`EnumDisplayDevices`、`QueryDisplayConfig`、`SetDisplayConfig`。

**DPI 陷阱**：多显示器不同缩放比时，坐标换算会疯。统一在**物理像素**空间里传坐标，逻辑像素只在注入前转换。

**负坐标陷阱**：虚拟桌面原点不一定在 (0,0)，副屏可能在负坐标区。

### 4.7 终端

`CreatePseudoConsole`（ConPTY，Win10 1809+）+ `ResizePseudoConsole`。

- Host：起 `powershell.exe` / `cmd.exe` / `wsl.exe`，读输出管道
- 传输：走可靠通道，纯字节流
- Android 渲染：`com.termux.terminal`（Apache-2.0），成熟
- Windows 渲染：`alacritty_terminal`（Rust crate）或 xterm.js in WebView

### 4.8 文件传输

复用同一条连接开第二条可靠流即可。要点清单：

- 分块 1MB，SHA-256 逐块校验
- 断点续传：记录已完成 offset，重连后从断点继续
- 海量小文件：先打包成 tar 流，避免每文件一次握手
- 长路径：`\\?\` 前缀
- 保留时间戳与权限
- 符号链接策略要明确（跟随 / 复制链接本身）
- 双向都要做（拉取 + 推送 + 拖拽）

### 4.9 延迟预算

局域网 1080p60 的合理目标：

| 环节 | 耗时 |
|---|---|
| 采集（DXGI） | 5~10 ms |
| 编码（硬件） | 5~15 ms |
| 网络 | < 5 ms |
| 解码（硬件） | 5~15 ms |
| 显示（含 vsync） | 0~16 ms |
| **合计** | **30~60 ms** |

体感门槛：< 40ms 几乎无感；40~80ms 可正常办公；> 100ms 打字开始难受。

**零拷贝是硬要求**：DXGI 纹理 → 编码器必须走 GPU 互操作。一旦中间做一次 CPU readback（staging texture），1080p60 会吃掉 1~2 个核，还多 5~10ms。

## 六、必踩的坑（提前知道能省两周）

1. **Session 0 隔离**：Windows 服务跑在 Session 0，**不能抓屏、不能注入输入**。必须是"系统服务（开机自启/守护）+ 用户会话 Agent（干活）"双进程结构。Sunshine 和 RustDesk 都是这么做的。
2. **UAC 安全桌面**：远程时看不到 UAC 弹窗，也点不了。要么像 RDP 那样注册凭证提供程序，要么接受"远端点不了 UAC"。
3. **DRM 内容**：Netflix 等走硬件保护路径，抓屏是黑屏。无解，别浪费时间。
4. **全屏独占游戏**：DXGI Duplication 会失败，必须回退 WGC 或要求游戏窗口化。
5. **防火墙**：LAN 发现要 UDP 广播/mDNS，还得加防火墙规则。这块你有经验（给 LocalSend 加过规则）。
6. **安卓后台杀进程**：前台服务 + 电池优化白名单，否则连一会儿就断。
7. **Wi-Fi 抖动**：哪怕 LAN，Wi-Fi 的延迟抖动也远大于有线。码率自适应比什么都重要。
8. **中文输入**：远程键盘输入中文切记传 Unicode 字符，不要传按键序列（IME 状态对不上）。
9. **多显示器 + 不同 DPI + 负坐标**：坐标换算的三重地狱，一定要在最早就统一到物理像素。
10. **驱动签名**：VDD 自研会卡在这里，先用现成开源版。

## 七、MVP 分阶段计划

### 阶段 0（第 1 周）：只证明视频链路

**做**：
- Windows：单文件 exe，DXGI 抓主屏 → MF 硬编 H.264 → UDP 发 NAL（自己定包头）
- Android：单 Activity，收 UDP → MediaCodec → SurfaceView

**不做**：输入、UI、虚拟屏、文件、终端、多显示器

**验收**：手机上看到 PC 桌面，1080p60，延迟 < 80ms，连跑 1 小时不崩。

> 这一周决定项目生死。**通了，后面全是体力活；不通，说明要么换路线，要么先补底层功底。**

### 阶段 1：能操作

输入回传（鼠标 + 键盘），光标本地绘制。

### 阶段 2：像个远程桌面了

多显示器切换、分辨率自适应、画质档位、剪贴板、快捷键。

### 阶段 3：虚拟显示器

集成 VDD，连上自动创建匹配客户端宽高比的虚拟屏，扩展屏模式，断开恢复。

### 阶段 4：文件与终端

第二条可靠流，文件管理器 UI，ConPTY 终端。

### 阶段 5：虚拟设备

`InjectSyntheticPointerInput` 的虚拟数位板（压力/倾角），虚拟触控，虚拟手柄。

### 阶段 6：UI 与动画

此时你攒了一堆"想让它更好看"的冲动，全部倒在这里。Rive / Lottie / 自绘都可以。

## 八、需要你拍板的三件事

**1. 你是想解决问题，还是想造东西？**

这一条决定一切。如果只是想"局域网内免费远程控制"，RustDesk 自建 + LAN 直连今天就能用，一分钱不花。如果造本身就是目的，那走自研，我把范围帮你收窄到能完成。

**2. 「复杂动画」具体指什么？**

是启动/连接时的过场、控制栏的形变、虚拟数位板的笔迹渲染，还是整个界面的视觉语言？如果只是几处动效，Rive 完全够；如果是要做一整套风格化的视觉语言，那才值得为 UI 框架妥协。

**3. 性能目标是「办公级」还是「游戏级」？**

- 办公级：100~150ms 可接受，软编也行，不用 Interception 驱动，不用管 DRM。工程量减半。
- 游戏级：必须硬编硬解 + 零拷贝 + 内核级输入注入 + HDR。工程量翻倍，且永远追不上 Parsec。
