# 选型定稿（截至 2026-11-13）

---

## 一、七条根决定

其余所有选型都是这七条的推论。

1. **内网与公网双模式**，两条传输各自优化到底，不做会员体系
2. **安卓控 Win + Win 控 Win**，不做 Win 控安卓，不做 Mac / Linux
3. **后端用 Rust**
4. **有视频的模式安静，没视频的模式才好动**
5. **手机控 Win 一律横屏**，竖屏只能通过扩展屏模式实现
6. **侧边栏常驻**，视频不占满整屏
7. **视频绝不参与 3D 变换**

第 4 和第 7 条是整套架构能收敛的根本原因。

---

## 二、总架构

```
主机 Windows：Rust（bin）
客户端：Godot 4 工程（Android + Windows 共用）+ 薄 Kotlin 胶水
核心：同一份 Rust crate，编译三次
      ├─ 桌面测试（cargo test，双端同进程）
      ├─ Windows 主机（bin）
      └─ Android（.so，经 godot-rust gdext 加载）
```

**边界原则：Rust 管字节，平台管纹理。**

Rust 不认识 Surface、窗口、纹理，只负责把画面变成有序的包、把包还原成帧。

---

## 三、主机侧（Windows）

| 环节 | 选型 | 备注 |
|---|---|---|
| 采集 | DXGI Desktop Duplication 主路，Windows.Graphics.Capture 兜底 | 全屏独占游戏会让 DXGI 失败 |
| 编码 | Media Foundation 硬件 MFT 起步 | 一条代码通吃 N/A/I 三家，后期再上 NVENC / AMF 原生 |
| 编码参数 | H.264 High、无 B 帧、CBR、无限 GOP、LowLatency 模式 | MVP 不用 H.265，保兼容 |
| 预览快照 | 1~2 fps、720p、WebP | 只给卡片用，非视频流 |
| 鼠标键盘 | SendInput | 绝对坐标归一化 |
| 触摸 | InjectTouchInput | 用户态，无需驱动 |
| 数位板 | InjectSyntheticPointerInput | 压感、倾角、笔擦全支持，用户态 |
| 虚拟显示器 | VirtualDrivers/Virtual-Display-Driver（IddCx） | 不自研驱动，签名过不去 |
| 终端 | ConPTY | Win10 1809+ |
| 显示器布局 | CCD API（QueryDisplayConfig / SetDisplayConfig） | 负坐标、DPI 都要处理 |

**必须做成双进程**：系统服务负责开机自启与守护，用户会话内跑 Agent 干活。服务在 Session 0，抓不了屏也注入不了输入。

## 四、传输：双后端

两套实现，同一条接口。

**抽象的边界切在「编码后的帧」，不是「包」。** 两种传输的包语义完全不同，一个自定义分片、一个 RTP，在包层做统一会让两层互相打架。

```rust
trait Transport {
    fn send_frame(&self, f: EncodedFrame);
    fn send_message(&self, m: Message);      // 可靠
    fn set_bitrate(&self, bps: u32);
}
```

### 4.1 内网模式（裸 UDP）

| 项 | 选型 |
|---|---|
| 视频 | UDP + 自定义分片，MTU 1200 |
| 包头 | `seq / frame_id / slice_id / ts / flags` |
| 重传 | 收端 NACK，等不到请求 IDR |
| 拥塞控制 | **无** |
| Pacing | **无**，一帧立刻全发 |
| 抖动缓冲 | **无** |
| 加密 | `snow`（Noise，X25519 + ChaCha20-Poly1305），每包 AEAD |
| 控制通道 | 并行 TCP，或同一套 UDP |

关键：局域网最奢侈的是「一帧在 0.5ms 内全到」。pacing 会把一帧摊平到整个帧间隔，那是给公网设计的，局域网上纯属自伤。

### 4.2 公网模式（webrtc-rs）

全套 ICE、DTLS-SRTP、NACK、FEC、拥塞控制、抖动缓冲，一样不少。

纯 Rust，不用编 libwebrtc。编码器吐 H.264 喂给 `TrackLocalStaticSample`，打包与重传它全包。

### 4.3 选路

同网段 + 直连成功 + RTT < 2ms，走内网模式。否则回落公网模式。允许手动强制。

### 4.4 网络迁移

笔记本从家里 Wi-Fi 切到手机热点，是内网模式掉到公网模式。这不该是重连新会话，而应该**保留会话状态，只换传输层**：编码参数、设备状态、剪贴板都留着，用户只感到画面卡一下。

做不好，移动场景会很脆；做得好，反而是个亮点。

### 4.5 画质档位

内网模式带宽近乎免费，码率上限开到 50Mbps 以上，可提供「近乎无损」档。公网模式严格 CBR 自适应。这才是「不为性能让步」的完整含义。

## 五、安卓客户端

| 环节 | 选型 |
|---|---|
| UI | Godot 4（3D 场景做主界面、卡片、转场） |
| 视频 | SurfaceView + `setZOrderMediaOverlay(true)` |
| 解码 | MediaCodec 异步模式 + `KEY_LOW_LATENCY` |
| 布局 | 横屏锁定，左侧常驻侧边栏，视频贴内容区 |
| 传感器 | 陀螺仪（200Hz）+ 加速度计，互补滤波 α≈0.98 |
| 帧预测 | Choreographer 回调里外推姿态到上屏时刻 |
| 阻尼 | `alpha = 1 - exp(-dt / tau)`，帧率无关 |
| 转场 | 卡片飞向内容区，精确对齐后硬切 |
| 扩展屏 | 按内容区比例 + DPI 建虚拟显示器 |

**图层顺序**（原生就支持，不需要透明合成）：

```
[默认层]      Godot SurfaceView 全屏 —— 侧边栏、主界面、终端
[media-overlay] 视频 SurfaceView 贴内容区
[窗口层]      普通原生 View —— 触摸指示、临时提示
```

Godot 全屏铺在底下，视频盖在内容区上，原生 View 还能再盖一层。

## 六、Windows 客户端

同一套 Godot 工程，两处不同：

- 视差触发源从陀螺仪换成**鼠标悬停位置**
- 视频走 D3D11 SwapChain + Media Foundation 硬解

统一的是设计 token（色彩、材质、层级、缓动曲线），不是触发器。

---

## 七、明确不做（第一期）

- 混合编码（dirty rect + 无损静态区）
- 音频传输
- Mac / Linux 端
- 游戏手柄虚拟化（ViGEmBus）
- 内核级输入注入（Interception）

---

## 八、五个待验证的风险

| # | 风险 | 什么时候验 |
|---|---|---|
| 1 | Godot 安卓端的 IME，终端打中文能不能用 | W3 |
| 2 | VDD 能不能报自定义 DPI / 物理尺寸 | W9 |
| 3 | SurfaceView + ZOrderMediaOverlay 与 Godot 并存的真机表现 | W2 |
| 4 | 横竖切换时 Surface 重建，解码器怎么续 | W9 |
| 5 | Rust 的 NDK 交叉编译与 gdext 打包链路 | W1 |
| 6 | `webrtc-rs` 的成熟度与硬编对接 | W8 |
| 7 | 内网 ↔ 公网传输切换的会话保活 | W8 |

第 1 条是唯一可能动摇 Godot 这个选择的。如果 IME 实在不行，终端模式的输入框用原生 EditText 盖上去，代价可控。

## 九、W1 目标

只做一件事，证明链路：

- Windows：DXGI 抓主屏 → MF 硬编 H.264 → UDP 发 NAL
- Android：收包 → MediaCodec → SurfaceView 上屏

不做输入、不做 UI、不做虚拟屏、不做动效。

验收：1080p60，端到端延迟 < 80ms，连跑一小时不崩。

测法：host 在画面角落渲染每帧变化的毫秒时间码，用另一台高帧率相机拍屏对比。

## 十、还给后期留着的位置

- **分层渲染**随时可以升级成**统一场景**（视频也参与透视），前提是 W2 的三项测试全过。现在不做，是因为不值。
- **混合编码**是文字清晰度的终极解，等主链路稳定再上。
- **Godot 换 Flutter** 也是一条退路，只要 Rust 核心和"Rust 管字节、平台管纹理"这条边界守住，换 UI 框架只需重写壳。

这三条都说明同一件事：**核心和壳分开，是所有决定的底气。**
