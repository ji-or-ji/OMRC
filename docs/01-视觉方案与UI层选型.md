# 视觉方案与 UI 层选型（Rust 核心确认后修订）

> **状态**：技术拆解部分有效（陀螺仪、传感器融合、帧预测、分层渲染）；UI 框架结论以 `docs/03-选型定稿.md` 为准（最终定为 Godot）。

> 约束变更：后端确定 Rust；动效目标为"游戏级"，且明确包含陀螺仪驱动的空间伪 3D。

---

## 一、先修正一个判断

上一版我否掉 Godot 的两条理由里，有一条**被你这句话推翻了**。

我当时说：Godot 是持续渲染的游戏循环，而远程桌面 80% 时间是静止画面，理想状态是零 GPU 占用，两者天生打架。

但如果你要的是**陀螺仪驱动的空间伪 3D**，那 UI 本身就永远在动。设备一倾斜，整层界面就要跟着视差位移，且必须跟手到 90/120Hz。这时候"持续渲染"不再是浪费，而是**刚需**。

所以结论要改成：

> Godot 作为**整个应用**仍然不合适（视频解码那条硬伤没变）。
> Godot 作为**纯 UI 图层**，现在是一个完全正当的选项。

这个区分很重要，别混在一起判断。

## 二、"陀螺仪空间伪 3D"到底是什么技术问题

先把名词拆开。它不是你想象中那种游戏引擎 3D，而是三层东西叠出来的错觉：

1. **透视矩阵**：给 UI 一个虚拟相机，让远处的东西缩小、近处的大
2. **分层视差**：不同深度的图层，在倾斜时位移量不同
3. **帧预测**：把传感器的延迟补掉，做到"手一歪画面就到了"

这三件事，**都不需要真正的 3D 场景**。它们是 2D 图形系统的标准能力。

### 2.1 传感器侧

不要用 `TYPE_ROTATION_VECTOR`。它融合了磁力计，室内会被金属家具和音箱干扰，表现为缓慢的莫名漂移。

用这个组合：

- `TYPE_GYROSCOPE`：最高 200Hz，提供高频角速度
- `TYPE_ACCELEROMETER`：提供低频的重力方向，作为绝对参考
- 互补滤波：`angle = α·(angle + ω·dt) + (1−α)·accelAngle`，α ≈ 0.98

理由是你要的是"短时精确、长时不漂"。陀螺仪短时准但会积分漂移，加速度计长时准但抖动大。互补滤波把两者的优点各取一半。

（`TYPE_GAME_ROTATION_VECTOR` 是备选，它已经做了陀螺+加速度的融合，但更新率通常只有 50Hz 左右，做 120Hz 视差不够跟手。）

### 2.2 渲染侧：帧预测是灵魂

这是决定"有没有游戏感"的那一步。

朴素实现：读到传感器 → 更新画面。结果是画面永远比手慢 1~2 帧，在 120Hz 屏幕上就是 8~16ms 的粘滞感，主观上像"界面在水里"。

正确实现（VR 里的 late latching / reprojection）：

```
Choreographer.postFrameCallback { frameTimeNanos ->
    val ahead = 预计出图时刻 - 最近传感器时刻
    val predicted = currentTilt + angularVelocity * ahead
    render(predicted)
}
```

把姿态外推到**这一帧真正上屏的时刻**，而不是"现在"。这一招能把响应延迟从"1~2 帧"压到"接近 0"，也是为什么 VR 头显不晕而普通手机 AR 晕。

### 2.3 阻尼：别写成 lerp

```
alpha = 1 - exp(-dt / tau)      // tau ≈ 0.05 ~ 0.12
smoothed += (raw - smoothed) * alpha
```

帧率无关。写成 `lerp(x, target, 0.1f)` 的话，60Hz 和 120Hz 手感完全不同，你调到 120Hz 舒服了，用户开省电模式掉到 60Hz 就变迟钝。

### 2.4 限幅

倾角映射到 ±8°，位移 ±24dp，超出饱和。持续大幅视差会让一部分人恶心，这不是玄学，是前庭系统和视觉信号冲突。必须给个"关闭视差"的开关，顺便满足无障碍要求。

## 三、致命冲突：视频层进不了 3D 场景

这是整个视觉方案的地基，必须在第二周就验证，否则全部动效构想都要重做。

`SurfaceView` 是**独立窗口图层**，由系统合成器直接贴到屏幕上，它**不接受任何 View 变换**。你把父容器旋转 30 度，视频画面纹丝不动。

也就是说：

> 只要用了 SurfaceView 播视频，视频就无法参与陀螺仪视差。

三条出路：

| 方案 | 延迟代价 | 控制力 | 工程量 |
|---|---|---|---|
| **A. TextureView** | +1 帧（8~16ms） | 够用 | 最小 |
| **B. SurfaceTexture → 框架外部纹理** | 同上 | 强，可放进自绘场景 | 中 |
| **C. AHardwareBuffer → 自己的 Vulkan/wgpu 渲染器** | **最低** | 最强，UI 与视频同一场景 | 最大 |

**推荐路径**：第一周用 A 验证手感，同时量出真实延迟代价。

- 若增量 < 15ms：方案成立，继续
- 若 15~25ms：接受，或者把视频层做成"不参与视差的锚定层"，只让控件层浮动（这其实是可接受的折中，很多设计本来就是这么做的）
- 若 > 25ms：上方案 C

**有个折中值得先想清楚**：视频画面**不参与**视差，只有控制栏、缩略图、通知条这些"近景"元素浮动，视频像嵌在一块玻璃板后面。这个效果其实更像 visionOS，而且完全没有延迟代价。可以作为兜底设计。

## 四、UI 框架再评估

### 4.1 Godot（现在值得认真考虑了）

**适合度**：视觉上限最高。

优势：
- 真 3D 相机、景深、反射、后处理链、粒子，全是引擎自带
- 可以把 2D UI 塞进 3D 空间（`SubViewport` 贴到 quad）
- 120Hz 无压力
- 同一工程导出 Android + Windows
- 动画系统（AnimationPlayer + Tween + 贝塞尔曲线编辑）确实好用

代价（仍然存在）：
- **视频帧进 3D 场景要自己搭桥**。Android 上 MediaCodec 输出的是 GL 外部纹理（OES），而 Godot 默认走 Vulkan，Vulkan 不能直接采样 OES。
  - 绕法一：用 Compatibility (GLES3) 渲染器，在 GDExtension 里直接画 OES。代价是被锁在较弱的三维管线里。
  - 绕法二：解码到字节缓冲（YUV420），Godot 里用 shader 做 YUV→RGB。简单可靠，代价是每帧一次 CPU 拷贝（1080p60 约 180MB/s），约 +2~3ms。现代手机扛得住。
- IME、文件选择器、剪贴板、前台服务，全要写平台插件。

### 4.2 Flutter（仍然是推荐值最高的那个）

**适合度**：工程现实最优。

优势：
- 伪 3D 视差本质是 `Matrix4` 透视 + 多层位移，Flutter 的 `Transform` 原生支持
- **外部纹理是 Flutter 的一等公民**：`TextureRegistry` + `Texture` widget，Android 和 Windows 都有。解码出的视频天然就是场景里的一个元素，可以被 `Transform` 3D 变换。这一条直接解掉了 Godot 最大的痛点
- Impeller 跟系统刷新率走，120Hz 没问题
- `FragmentProgram` 能做片段着色器，模糊、扭曲、色差这类后处理够用
- IME、文件选择器、权限、前台服务，插件生态成熟
- RustDesk 已经证明了这套组合能做出可用的跨端远程桌面

劣势：
- 真 3D 几何、景深、反射、粒子，做不了（伪 3D 用不着，真需要时再说）
- 后处理链不如引擎完整

### 4.3 判定线

一句话：

> **要的是"透视 + 视差 + 缓动 + 少量 shader 效果" → Flutter。**
> **要的是"真 3D 几何 + 景深 + 反射 + 粒子 + 完整后处理链" → Godot。**

我个人建议 Flutter，因为你描述的核心是"空间感"，而空间感 90% 来自透视、视差和跟手度，不来自三维几何。

## 五、一个没人提醒你的设计矛盾

**PC 端没有陀螺仪。**

你的视觉语言以姿态输入为触发器，而 Windows 客户端根本不存在这个输入源。这意味着"多端统一"在你这里会出现一个真实的裂缝：

- 要么 PC 端用鼠标位置模拟（视差跟指针走），效果像但不一样，且鼠标在窗口内是离散的
- 要么两端的视觉语言分家，共享材质与曲线，交互方式各自为政
- 要么 PC 端干脆不做视差，只做静态的层叠视觉

我的看法：**统一的是设计 token（色彩、材质、层级语义、缓动曲线、景深关系），不是触发器。** 手机用陀螺仪，PC 用指针悬停位置，两端看起来是同一个世界，用起来各顺各的手。这才是可落地的"多端统一"。

这一条建议早点定，因为它影响两端的组件设计。

## 六、Rust 核心的边界

"上 Rust 后端"要先说清楚边界，否则很容易变成"什么都用 Rust 写然后被平台细节拖死"。

```
core/                      纯 Rust，无平台依赖
  proto/      消息定义与序列化（postcard）
  transport/  UDP 视频通道 + 可靠控制通道（QUIC 或 TCP）
  video/      分片、重组、NACK、IDR 请求、码率反馈
  input/      统一事件模型（触摸 / 鼠标 / 笔 / 键盘 / 手柄）
  fs/         文件传输
  term/       终端字节流
  session/    会话状态机、鉴权、能力协商

platform/                  按 cfg 编译，Rust 直接调系统 API
  win/        DXGI / WGC 采集、MF 编码、SendInput、CCD、ConPTY、VDD 控制
  android/    MediaCodec、SensorManager、纹理桥、前台服务

ffi/
  jni/        Android 侧
  c/          Windows 侧
```

**Rust 能干哪些平台活**：

- Windows 全都能干。`windows` crate 覆盖 DXGI、Media Foundation、SendInput、ConPTY、CCD，NVENC 有现成绑定。这是 Rust 的主场
- Android 大部分能干。`ndk` crate 有 `AMediaCodec`、`ASensor`。但纹理注册、前台服务、Activity 生命周期这些，终究要一层薄 Kotlin

**所以准确的表述是**：Rust 做全部业务逻辑与 Windows 平台层，Android 保留一层最小 Kotlin 胶水（大概几百行，负责 Activity、纹理注册、服务）。

**crate 清单**：`tokio`、`quinn`、`serde` + `postcard`、`rustls`、`lz4_flex`、`zstd`、`windows`、`jni`、`ndk`、`tracing`、`flutter_rust_bridge`（若选 Flutter）。

## 七、修订后的阶段计划

原计划里插入了两个必须先做的验证。

| 阶段 | 内容 | 关键验收 |
|---|---|---|
| **W1** | DXGI 采集 → MF 硬编 → UDP → MediaCodec → SurfaceView | 手机上看到桌面，延迟 < 80ms |
| **W2** | **把 SurfaceView 换成 TextureView / 外部纹理** | 量出真实延迟增量。这一步定生死 |
| **W3** | **陀螺仪视差原型**（静态图，不接视频） | 融合 + 帧预测 + 分层，手感调到位 |
| **W4** | 视差与视频合成 | 视频层与控件层同场景，确认晕动症可接受 |
| W5~6 | 输入回传（鼠标 + 键盘 + 光标本地绘制） | 能正常打字 |
| W7~8 | 多显示器、分辨率自适应、画质档位 | 像个远程桌面了 |
| W9+ | VDD 虚拟显示器 | 扩展屏可用 |
| W10+ | 文件传输 + 终端 | |
| W11+ | 虚拟数位板（`InjectSyntheticPointerInput`） | 压感可用 |
| 最后 | 全面打磨动效与视觉 | |

**W2 和 W3 是新增的，也是最该早做的**。因为这两个决定了你的视觉构想能不能成立。如果 W2 测出延迟不可接受、W3 的视差又让人晕，你要有第二套视觉方案（比如"视频锚定不动，只有近景控件浮动"）。

**建议在 W3 阶段就用静态图把动效调到位**，不要等视频接进来。传感器融合的调参是一件需要反复感受的事，跟视频链路是独立的。

## 八、新增的风险

1. **晕动症**：视差做过头会让人恶心。限幅、可关、默认温和。
2. **功耗**：120Hz 合成 + 视频解码 + 3D 变换，中端机可能在 4~6W。静止 3 秒后降频或暂停视差。
3. **刷新率请求**：Android 11+ 要显式 `setFrameRate()`，否则系统可能锁 60Hz，你的 120Hz 动效白做。
4. **PC 端无对应输入**：见第五节。
5. **视频帧率与刷新率不同步**：60fps 视频在 120Hz 屏上要重复帧，策略不当会有节奏感抖动。可以试试在 60Hz 内容时把合成降到 60Hz。
6. **TextureView 的额外开销**：多一次 GPU 合成，中低端机可能掉帧。要在真机上测，模拟器不算数。

## 九、还需要你回答的

1. **你脑子里的画面，视频画面本身参与空间吗？**
   比如屏幕是"斜着立在空间里、有厚度、会随倾斜改变视角"，还是"屏幕平贴、只有周围的控件在浮动"？
   前者要方案 C，后者 TextureView 够用，工程差三倍。

2. **"复杂动画"里有没有真 3D 物体？**
   旋转的 3D 图标、粒子、景深虚化？还是全是 2D 的位移、缩放、透明度、模糊？

3. **有没有后处理需求？**
   比如背景虚化、色差、噪点、暗角、光晕。有的话，Flutter 的 `FragmentProgram` 能覆盖大部分，但复杂合成链可能不够。

答完这三个，UI 框架就能锁死了。
