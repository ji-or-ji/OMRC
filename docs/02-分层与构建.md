# 代码分层、构建与验证

---

## 一、边界原则：Rust 管字节，平台管纹理

这是整套架构唯一需要记住的一句话。

**Rust 的职责**：一串字节进，一串字节出。它不认识 Surface，不认识窗口，不认识窗口句柄。它只负责"把 host 的画面变成有序的包发出去"和"把收到的包还原成有序的帧"。

**平台的职责**：把系统的东西交给 Rust，或者把 Rust 的东西交给系统。采集用的纹理、解码要投的 Surface、注入输入用的 API、传感器的回调，全是平台层。

为什么这么切：

1. 字节层是纯逻辑，可以在桌面机上跑测试，不需要设备
2. 纹理层天然绑定 UI 框架，换框架时只改这层
3. JNI 边界越窄越好。传字节用直接内存块，传纹理就是灾难

## 二、三端结构

```
connecter/
├─ core/                    # 纯 Rust，零平台依赖
│   ├─ proto/               # 消息定义、序列化
│   ├─ transport/           # UDP 视频通道 + QUIC/TCP 控制通道
│   ├─ video/               # 分片重组、NACK、IDR 请求、码率反馈
│   ├─ input/               # 统一事件模型 + 编码
│   ├─ fs/                  # 文件传输协议
│   ├─ term/                # 终端字节流
│   └─ session/             # 状态机、鉴权、能力协商
│
├─ core-ffi/
│   ├─ jni/                 # 给 Kotlin 用
│   └─ gdext/               # 给 Godot 用（godot-rust）
│
├─ host-win/                # Windows 主机
│   ├─ capture/             # DXGI / WGC
│   ├─ encode/              # Media Foundation / NVENC
│   ├─ inject/              # SendInput / InjectSyntheticPointerInput
│   ├─ display/             # CCD API、VDD 控制
│   └─ conpty/
│
└─ client/
    ├─ android/             # Godot 工程 或 Flutter 工程
    └─ windows/             # 同上，共用 UI 代码
```

`core` 编译三次：

- 桌面测试用（`cargo test`）
- Windows 主机用（bin）
- Android 用（`.so`，由 GDExtension 或 JNI 加载）

**同一份协议实现**，这是整个方案最大的收益。

## 三、为什么值得在手机端也用 Rust

不是因为性能。Kotlin 收一个 30Mbps 的 UDP 流毫无压力。

真正的原因是**协议层的可测试性**。

远程桌面这类项目最经典的死法：host 和 client 的线格式悄悄不一致，你对着两边的日志找三天，最后发现是某个字段的字节序或者某个长度前缀差了一位。

如果核心是同一份 Rust 代码，你可以这样做：

```rust
#[test]
fn 分片重组能扛住乱序和丢包() {
    let mut tx = HostCore::new(test_config());
    let mut rx = ClientCore::new(test_config());
    let frames = tx.encode_test_frames(300);
    let wire = tx.pump();                    // 拿到要发的字节
    let noisy = lose_and_shuffle(wire, 0.05);  // 丢 5% 并打乱
    rx.feed(noisy);
    assert_eq!(rx.completed_frames(), expect);
}
```

在 CI 里跑，不需要手机，不需要模拟器，不需要开机。只要改协议就会立刻发现问题。

这套东西如果用 Kotlin 重写一遍协议，就做不到了。你会得到两份永远在漂移的实现，和一种"改 host 之前先祈祷"的开发体验。

**这是我在这个项目里能给你的最值钱的建议之一。**

## 四、代价，说清楚

**1. 构建复杂度**

`cargo-ndk` 交叉编译 4 个 ABI（arm64-v8a、armeabi-v7a、x86_64、x86），接进 Gradle。第一次配置大概要半天，之后就顺了。建议只出 arm64-v8a + x86_64（真机 + 模拟器），把体积砍一半。

**2. 调试体验**

Rust panic 的栈混在 Java/Kotlin 栈里，一开始会烦。配好 `tracing` 输出到 logcat，习惯就好。

**3. 边界开销**

每帧都要过 JNI 的话会很痛。所以设计上要**批量**：Rust 侧维护一个环形缓冲，Android 侧一次 `getDirectBufferAddress` 拿到指针后反复用，不要每帧一次调用。

**4. 线程模型**

tokio runtime 在 Godot 进程里跑没问题，但要注意不要把回调打到 Godot 的非主线程上。

## 五、如果选 Godot，路径是 godot-rust

`gdext`（godot-rust）是成熟的 GDExtension Rust 绑定，支持 Android 导出。

结构上：

```
core-ffi/gdext/  →  编译成 .so  →  放进 addons/  →  Godot 场景里当节点用
```

Rust 侧暴露一个 `ConnectorNode`，Godot 侧 GDScript 直接调用。协议、传输、重组全在里面。UI 在 Godot 里正常做。

这条路很干净。**但有个前提要先确认**（见第六节）。

## 六、要纠正你一个假设

你说"反正 Godot 本身就擅长 2D"。

2D 确实擅长，但**Godot 的 2D 管线是正交投影，没有透视相机**。

伪 3D 的核心是透视：近大远小、平行线汇聚。这在 Godot 2D 里做不到，除非你自己写一个做单应变换的 canvas shader，那会很别扭。

标准做法是：**用 3D 渲染器**，把 2D UI 画进 `SubViewport`，再贴到 3D 空间里的一个 quad 上。

于是你会用到 3D 渲染器，于是视频纹理进场景的问题又回来了，而且在 Godot 上更贵：

| 路径 | 成本 |
|---|---|
| 解码到 YUV 字节缓冲 → shader 转 RGB | 每帧一次 CPU 拷贝 + 纹理上传。1080p60 约 180MB/s，加 2~4ms |
| 解码到 OES 外部纹理 → 导入 Vulkan | 零拷贝，但 GL/Vulkan 互操作在 Android 上是深坑 |
| 被迫用 Compatibility (GLES3) 渲染器 | 能直接画 OES，但三维管线变弱 |

所以"Godot 擅长 2D"这句话，在你需要的**透视**这件事上，不成立。

## 七、我上次说满了一句，现在收回一半

上一版我说 Flutter 的 `Texture` widget "能直接被 `Transform` 做 3D 变换"。

这话说得太绝对了。Flutter 的 `TextureLayer` 是引擎级的合成图层，它的变换能力有边界，透视变换能不能正确作用在上面，**必须原型验证**，不能靠文档推断。

这跟 Godot 那边是同一种风险，只是方向不同。

所以第六节那张表，其实应该是两个框架各有一个"待验证的红点"：

- **Godot**：视频帧进 3D 场景，零拷贝路径难；CPU 路径带宽高
- **Flutter**：外部纹理能不能吃透视变换；吃不了就只能退回"视频不参与变换"

## 八、真正的解法：分层渲染

写到这里，最该被抬出来的是那个我一直当兜底的方案，现在我建议把它当**首选**。

把画面拆成两层：

```
┌────────────────────────────────────┐
│ 空间层（引擎渲染，参与视差）        │
│   控制栏、缩略图、光晕、景深元素     │
│   ← 陀螺仪 / 鼠标悬停驱动           │
├────────────────────────────────────┤
│ 内容层（原生表面，不参与变换）       │
│   远程画面                          │
│   ← SurfaceView / SwapChain         │
└────────────────────────────────────┘
```

两层共享同一套 depth 参数和缓动曲线，视觉上看起来在同一个空间里；技术上是两条独立管线。

**收益**：

1. 视频层留在 `SurfaceView`，延迟最低，零额外拷贝
2. 引擎那边只处理矢量图形和纹理，帧率稳
3. 两个框架的那个"红点"都不再是阻塞项
4. 视觉上并不会差：隔着玻璃看内容，本来就是现在的设计语言（visionOS 就是这么干的）

**代价**：视频画面本身不倾斜、没有厚度、不随视角变化。它是一块"锚定的画框"。

如果你想的是"屏幕斜立在空间里、随倾斜改变视角"，那就必须走统一场景，风险和时间都要加倍。

这是一个需要你现在拍板的取舍，因为它决定了后面所有事。

## 九、W2 验证清单（三件事，一次测完）

用同一套最小代码，测三组数据。

**1. 延迟基线**

`SurfaceView` + 1080p60，测端到端延迟。

测法：host 在画面角落渲染一个每帧变化的高精度时间码（毫秒），手机用另一台高帧率相机拍屏，对比时间差。这是远程桌面延迟测量的标准土办法，比任何软件打点都准，因为它把所有真实开销都算进去了。

**2. 纹理路径增量**

同样条件换成 `TextureView` / 外部纹理，量出延迟增量。目标 < 15ms。

**3. 透视变换可行性**

- Godot：3D quad + `SubViewport` 贴图，看能否稳定 60fps 且延迟可接受
- Flutter：`Transform` 包 `Texture`，看透视是否生效、有无掉帧

顺带用 `adb shell dumpsys batterystats` 记一次功耗基线。

## 十、下一步

需要你回答一个问题，二选一：

**A. 分层渲染**：视频锚定不动，控件和装饰在空间里浮动。
　风险最低，W2 只需测延迟，两个框架都成立，我可以直接开始搭骨架。

**B. 统一场景**：视频本身也参与透视和视差。
　视觉上限最高，但 W2 要先把上面三个测试跑完，有一项不过就得回退到 A。

选 B 也可以，只是要接受"可能做不成，得退回来"这个概率。我的建议是先按 A 搭骨架，同时在 W2 并行跑 B 的可行性测试。骨架不依赖这个答案，测试结果出来再决定视觉层怎么写。

这样你既不会白等，也不会把架构押在一个未验证的假设上。
