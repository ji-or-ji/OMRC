# W1a：Windows 闭环实测

> 2026-11-13 完成。主机端（`omrc-host`）与回环接收端（`omrc-client`）同机跑通：
> 抓屏 → GPU 转 NV12 → 硬件 H.264 → 裸 UDP 分片 → 重组 → 软解 → 上屏。

---

## 一、跑法

```powershell
# 终端 A：回环接收端（开一个窗口）
target\release\omrc-client.exe --listen 0.0.0.0:9100

# 终端 B：主机端，推 6 秒
target\release\omrc-host.exe play --peer 127.0.0.1:9100 --seconds 6 --fps 60 --encoder hw
```

其他命令：

```powershell
target\release\omrc-host.exe list    # 枚举显示器
target\release\omrc-host.exe mft     # 枚举 H.264 编码器 MFT 与异步/D3D 能力
target\release\omrc-host.exe probe   # 抓 3 秒，量采集与转换开销
target\release\omrc-client.exe --decode-dump stream.bin   # 离线回放码流
```

`--encoder` 可选 `auto` / `hw` / `sw`。**软件编码器有 550ms 固有时延，只能用来调试链路，不能实际用。**

## 二、实测数据（1920×1080，本机回环）

| 项 | 硬件（NVENC via MF） | 软件（MS H.264 MFT） |
|---|---|---|
| 采集帧率 | 37~41 fps | 31~37 fps |
| 采集 + 转 NV12 + 编码 | **0.3~0.5 ms** | 4~6 ms + 1.5 ms |
| 编码器内部滞后 | **26 ms**（约 1 帧） | **560 ms**（约 17 帧） |
| 客户端解码 | 7.6 ms/帧 | 7.6 ms/帧 |
| 客户端绘制 | 2.5 ms/帧 | 2.5 ms/帧 |
| 端到端延迟 | **37 ms** | 560 ms + |

- 编译：`cargo build --release`
- 延迟口径：帧的 `pts_us` 是采集时刻的墙钟微秒，客户端在解出这一帧时取 `now - pts`。
  同机回环时两端时钟同源，这个数反映「采集 → 解码完成」的全过程，不含显示器的扫描延迟。
- 验收线是 80ms，硬件路径达标。

### 为什么软件编码器不能用

Microsoft 的软件 H.264 编码器不认 `CODECAPI_AVEncCommonLowLatency` / `CODECAPI_AVEncCommonRealTime`，
固定攒一批帧再出（实测 17 帧）。这不是配置问题，是编码器实现的取舍。
W1a 期间它只是用来把「传输 + 解码 + 上屏」先验证一遍的拐杖。

## 三、链路结构

```
DXGI Desktop Duplication
  → 拷贝进自己的纹理（可写、可叠字）
  → 时间码叠字（GDI 小 DIB + UpdateSubresource）
  → D3D11 Video Processor：BGRA → NV12（显存内，0.2ms）
  → MF 硬件 H.264（异步 MFT + D3D11 设备管理器，零拷贝）
  → fragment() 32 字节包头 + 1168 字节载荷
  → UDP（无 pacing、无抖动缓冲、一帧立刻全发）
        ↓
  → Reassembler（容忍乱序/重复，缺片不吐半帧）
  → MF H.264 解码（同步软解，逐帧按序）
  → NV12 → BGRA（CPU，7.6ms/帧）
  → GDI StretchDIBits 贴窗口（2.5ms）
```

客户端两个线程：

- **收包线程**：死循环 `recv_from` + 重组 + 入队，不等任何东西。内核缓冲不积压，延迟才不涨。
- **UI 线程**：抽消息、逐帧解码、只上屏最新一张。解码不能跳帧（H.264 参考链），但显示可以。

## 四、踩过的坑（都是会再踩的）

### 1. 传了适配器就必须用 `D3D_DRIVER_TYPE_UNKNOWN`

`D3D11CreateDevice` 传 `pAdapter` 又传 `HARDWARE`，直接 `E_INVALIDARG`。
桌面复制必须用输出所在的那块适配器，所以这条一定会撞上。

### 2. 硬件 MFT 不实现 `IMFAttributes`，QI 会返回 `E_NOINTERFACE`

NVIDIA / Intel 的硬件编码器 MFT 拿 `QueryInterface(IID_IMFAttributes)` 是要不到的，
但异步解锁（`MF_TRANSFORM_ASYNC_UNLOCK`）偏偏要写这个属性。
**正路是 `IMFTransform::GetAttributes()`**，它不依赖 QI，能拿到同一个属性存储。

### 3. 异步 MFT 的调用顺序

- 解锁 → 设类型 → `MFT_MESSAGE_NOTIFY_BEGIN_STREAMING` → `MFT_MESSAGE_NOTIFY_START_OF_STREAM`
- 只有收到 `METransformNeedInput` 才能 `ProcessInput`
- 只有收到 `METransformHaveOutput` 才能 `ProcessOutput`
- 第一次 `ProcessOutput` 可能在没有输入时就拿到一个 `E_UNEXPECTED`，要当成「没东西可拿」吞掉

### 4. D3D11 感知的硬件 MFT 必须先给设备管理器

`MF_SA_D3D11_AWARE == 1` 的 MFT，不给 `MFT_MESSAGE_SET_D3D_MANAGER` 就喂系统内存样本，
`ProcessOutput` 直接 `E_UNEXPECTED`（不是明确的参数错误，特别难猜）。
给了管理器之后，输入也必须是 D3D11 纹理（`MFCreateDXGISurfaceBuffer`），否则同样失败。

### 5. 解码器输出是宏块对齐的，缓冲区要按 **coded** 尺寸算

1080p 的帧解出来是 1088 行。按可见尺寸分配输出缓冲，解码器报
`CopyDecodedFrame failed (0x80004005)`。可见尺寸要从
`MF_MT_MINIMUM_DISPLAY_APERTURE` 读，不能直接用 `MF_MT_FRAME_SIZE`。

### 6. 客户端别在 UI 线程里边收包边解码

一开始单线程 `recv → 解码 → 画`，`SO_RCVBUF` 里积压，延迟稳定在 500ms 以上。
拆成「收包线程只入队」+「UI 线程逐帧解码、只上屏最新」，延迟掉到 37ms。

| 项 | 说明 |
|---|---|
| 输入注入 | W1a 不做，`core/input.rs` 的模型已在 |
| 关键帧请求 | 编码器有 `request_keyframe()`，NACK 链路等 W2 一起接 |
| 重复回复 / 丢包恢复 | 内网目前零丢包，NACK 只在 W2 真机联调时接 |
| 断线重建 | 复制链路断了（切分辨率 / 全屏独占 / 锁屏）目前直接退出，W2 做重建 |
| 安卓端 | W1b，需要先装 Android SDK / NDK |
| 编码器滞后 26ms | NVENC 经 MF 的固有队列，想再压要绕开 MF 直连 NVENC（W8 之后再说） |
